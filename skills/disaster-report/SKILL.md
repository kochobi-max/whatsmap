# ADRC 大規模災害レポート — 統一フォーム・日次/1日2回アップデータ

災害ごとにスキルを複製しない。**1つの統一フォーム＋1つのジェネレータ＋災害ごとのJSON**で運用する。
毎回、一次情報から数値・行を更新して再生成し、OneDriveへ保存し、研究部あての更新メールを送る。

**ユーザーへの説明はすべて日本語で行う。**

### 新規イベントの追加

## 1. データ更新 — `events/<GLIDE>.json`

出典の階層を厳守: **公式(official) > 報道(media) > 確認中(tbc)**。公式値を下位ティアで上書きしない。

1. `references/sources/<ISO3>.md` を読み、その国の情報源を**記載順に**当たる
2. `references/sources/_global.md` の国際ソース（ReliefWeb / GDACS / Sentinel Asia / 国際災害チャーター）を当たる
3. 取得した数値を `d.damage.*` に反映し、`sourceDate` と `sourceURL` を必ず記録する
4. 新規被害・対応は `d.damage_highlights[]` と `d.timeline[]` に**行を追加**する
5. `d.meta.stamp`（現在JST）、`d.meta.update_date`（dd/mm/yyyy）、`d.meta.edition`、
   `d.meta.timeline_range_en/ja` を更新する。**JSONに直接書き込む**（buildのmeta刻印は環境により永続しない）
6. P1概要 `d.event.summary_en/ja` も最新情報で書き換える。
   **概要文には字数上限がある**（表紙の黒帯に収める）。EN 1,450字・JA 530字を目安とし、超えたら文を削る

### 落とし穴（実際に起きた事故の記録）

- **報番号を取り違えない。** 「第47報」と「第48報」の数値を混ぜない
- **被害区分を取り違えない。** 「一部破損」と「避難指示世帯数」は別物
- **時系列に行を追加したら必ず時刻順に並べ直す。** 末尾にappendしただけでは同じ日の既存行より後ろに来る。
  先頭付近には日付なし／日のみの行があるので、配列全体を機械的にソートせず、追加行を正しい位置へ挿入する
- **数値を差し替えたら、それを引用している他のページも同じ報に揃っているか点検する。**
  取りこぼしやすいのは表の列見出しの `as_of`、注記枠の `note_en/ja`、分野別 `findings`、
  ハードコードされたリンク集の報番号
- 確定済みの履歴は消さない。`[[links]]` や構造は保持する
- **安易に大きい数字へ乗り換えない。** 前提が疑わしければ数値だけでなく前提を問う

## 2. 数値急変ゲート（新設・BLOCKING）

機械QAでは検出できない取り違えを捕まえるための人的ゲート。

前報（JSONの更新前の値）と比較し、**いずれかに該当したら生成は続けるがメールは送らず**、
荒木田（`ma-arakida@adrc.asia`）に確認を求める。

| 条件 | 想定される原因 |
|------|--------------|
| 死者数が前報比 +50% 以上 | 報番号の取り違え / 別災害の数値の混入 |
| 住家被害が前報比 2倍以上 | 被害認定調査の進展（正常）か、区分の取り違えか |
| いずれかの数値が**減少** | 訂正報か、古い報を新しい報と誤認したか |
| ティア降格（official → media で上書き） | 公式値を報道値で上書きしている |

確認メールには **前報値・今報値・出典URL・出典日** を並べて示す。
承認されたらそのまま送信、否認されたら該当箇所を修正して再実行する。

> 住家被害の急増が認定調査の進展によるものと確認できた場合は、
> 更新メールに「被害の拡大ではなく被害認定調査の進展による」と補足を入れる。

## 3. ビルド（統一フォーム）

言語レイヤ・フォント・レイアウトの仕様は**全イベント共通**。イベント固有の分岐を入れない。

### 3-0. ビルド前の検証（省略不可）

```bash
node generator/scripts/resolve_event.js --event <GLIDE>
```

| 終了コード | 次の動作 |
|-----------|---------|
| `0` OK | ビルド → OneDrive保存 → **メール送信** |
| `2` HOLD | ビルド・保存はする。**メールを送らず**、§2 の確認メールに切り替える |
| `3` INVALID | **ビルドしない。** 表示された違反箇所をイベントJSONで直してから再実行 |

`--event` を省略すると `meta.status: "active"` の全イベントを対象にする（定期タスク用）。

### 3-1. ビルド

```bash
for L in ja en; do
  U=$(echo $L | tr a-z A-Z)
  LANG_OUT=$L UPDATE_DATE="$(TZ=Asia/Tokyo date '+%d/%m/%Y')" \
    EVENT="events/<GLIDE>.json" \
    OUT="$OUTDIR/${FILEBASE}_$U.pptx" node generator/scripts/gen_deck.js
done
cd "$OUTDIR" && soffice --headless --convert-to pdf --outdir "$OUTDIR" *.pptx
```

`FILEBASE` は `meta.filebase`（例: `ADRC_EQ_JPN_Kumamoto_20260728`）。
出力は `<FILEBASE>_JA.pptx/.pdf` と `<FILEBASE>_EN.pptx/.pdf` の4ファイル。

- **作業ディレクトリ・出力ディレクトリは毎回新しい名前にする**（例 `/tmp/w0817`, `/tmp/o0817`）。
  再利用すると前回実行分が別ユーザー所有で残っていて `rm` も上書きも Permission denied になる
- スキル同梱の `generator/` は読み取り専用なので、書き込み可能な作業ディレクトリへコピーしてから作業する
- `npm install pptxgenjs` が必要な場合がある

### 言語レイヤ（壊さないこと）

`LANG_OUT=ja|en|bi` で出し分ける。日英併記版（`bi`）は後方互換のため生成可能だが**通常は作らない**。

- イベントJSONは**英日同居のまま**でよい。コード側が実行時に分離する。
  **JSONを英日分離した構造に作り替えてはいけない**（次回の更新で元に戻り、二重管理になる）
- 分離規則: **最初の日本語文字より前にある最後の区切り**で切る。
  区切りは `' / ' ' — ' ' – ' 全角空白 '. ' 2連スペース '; ' ' · '`
- 自動分離できない例外は `SPLIT_OVERRIDE` テーブルで個別指定する
- **言語タグ付きフィールド（`*_en` / `*_ja` / キー `en` `ja`）は絶対に分割しない**
- **位置依存の配列**（既に英日が別要素）は要素位置で言語を選ぶ
- `source` フィールドは英語表記のみなので、日本語版では対訳表で和訳する。
  対訳表は `references/sources/<ISO3>.md` に国ごとに持つ（FDMA→消防庁 等）
- 単言語版は本文量が半分になるので、**固定高のバンドや固定行数のページ分割を言語に応じて調整する**。
  ページ数を減らすためにフォントを小さくするのは不可

### フォント（確定仕様・変更しないこと）

`const FONT = "Meiryo", SERIF = "Cambria", JFONT = "Meiryo";`

本文・表・箇条書きは **Meiryo**。英語の見出しのみ Cambria。日本語版では和文見出しもMeiryo。
サンドボックスにMeiryoは無いので `fonts.conf` で Meiryo→Noto Sans CJK JP にエイリアスし `fc-cache -f`。
**Meiryoは字幅が広い。** フォントやサイズを変えた後は必ず全ページを目視確認する。

## 4. 視覚QA — 毎回、PDFを画像化して目視する

テキスト抽出だけでは不十分。**両言語とも**実施する。

機械検査:
- `qa_overflow_check.py <pdf>` … 「出典/Sources」行より下へのはみ出し。**両言語とも overflow pages: 0**
- 言語混入: 英語版PDFに日本語文字が無いこと（`pdftotext | grep -P "[\x{3040}-\x{30ff}]"` が0件）
- DRAFT / TBD / PLACEHOLDER / TODO が0件、フッターの日付が当日のものだけ

目視（`pdftoppm -r 95 -png -f N -l N`）。**QA画像は出力フォルダ配下（Readツールが読めるパス）へ書き出す。**
既存のQAディレクトリは削除できないことがあるので毎回新しいディレクトリ名にする。
最低限、表紙・時系列の最終2ページ・被害状況の全ページを見る。

**再発させないこと**:
- **DRAFT行を一切出さない**（表紙左上・全ページ左下とも削除済み。復活させない）
- **表・本文が「出典 / Sources」行やオレンジの注記枠に重ならない。**
  行が増えたら、フォントを小さくして詰め込むのではなく、行数を減らしてページ分割するか行高を詰める
- **表紙**: 黒帯に概要文が完全に収まり、かつ帯の下に大きな空洞ができない（帯は可変高）。
  地図ラベルは1行（`wrap:false`, 9.5pt）。地図は**4:3厳守**
- **見出し枠は `w:11.3, wrap:false, shrinkText:true`**
- **表の内容が本文の記述と食い違っていないか**（表が古い報のままになっていないか）
- 時系列が時刻順に並んでいること

**PCがやるのはコピーだけ。ビルドはしない。**

PC側は台帳の `BUILT_DATE_JST` が**当日でなければコピーしない**（`STATUS: SKIP stale-dist`）。
クラウド側の朝のビルドが落ちた日に、前日のファイルを置き直して
「本日更新しました」というメールを出さないため。

**公開記録**（`_published/<GLIDE>.json`）は、PCが実際にコピーできたときだけ書かれる。
**この記録が当日のものでなければメールは出ない。** 本文に「OneDriveに保存しました」と
書く以上、保存されていないまま送ることがあってはならない。

| PC側の結果 | メール |
|---|---|
| コピー成功・記録がプッシュされた | 送る |
| コピーはできたが記録をプッシュできなかった | **送らない**。通知だけ |
| PCが動かなかった | **送らない**。通知だけ |

（ユーザーの明示指示・2026年8月13日）。本文は「荒木田」で終わり。

#### メールの文体（厳守）

**事実以上の評価・演出を含む表現を使わない。** 観測された数値・公表内容と、その出典だけを書く。

- 使わない例: 「正念場」「山場」「予断を許さない」「深刻な事態」「懸念される」「急務である」
  「危機的」「かつてない」「重要な局面」「注視が必要」など、書き手の評価や情緒を足す語
- 「現在の局面」の段落は、**進行中の事実の列挙**にとどめる
  - 可: 「断水は3市町で継続し、8月末の解消を目標としている。被害認定調査は8市町で実施中。」
  - 不可: 「断水の解消が急務であり、8月中旬以降が正念場となる。」
- 見通しを書く場合は、**発表主体を明示した引用**の形にする
- レポート本体（PPTX）の「評価」欄は分析文なので、根拠を示したうえでの解釈は可。
  **ただしメール本文には持ち込まない。**

## 画像

`generator/images/` に視覚素材を同梱し、**毎回そのまま再利用**（オンライン取得しない）。
イベント固有の画像は `generator/images/<GLIDE>/` に置き、JSONの `d.images.*` から参照する。
差し替えは `<key>.png` を置換（`<key>_manual.png` 優先）。

### 図の中に文字を入れるときは、言語ごとに持つ

```
images/<GLIDE>/locator_world.png      共通（言語別が無いときの落とし先）
images/<GLIDE>/locator_world_en.png   英語版のデッキが使う
images/<GLIDE>/locator_world_ja.png   日本語版のデッキが使う
```

探索順は `<key>_manual_<lang>` → `<key>_manual` → JSON の指す `_<lang>` 版 →
JSON の指すファイル → `<key>_<lang>.png` → `<key>.png`
（`apply_language_figures.js`）。**言語別が無ければ従来どおり共通のものが出る。**

2026-08-28、ネパールの位置図を1組だけ作り、日本語の注記を入れたまま
英語版にも使った。**英語版の表紙に日本語が出た。**
そのときは「図の文字は英語だけにする」で塞いだが、これは後退で、
日本語版の読み手が図の中だけ英語を読まされる。
