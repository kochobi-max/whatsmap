## 渡すものの作り方

- **改行コードは向きが2つある。両方おさえること。**（→ 詳細は末尾の節）

  | 対象 | 正しい改行 | 間違えるとどうなるか |
  |---|---|---|
  | `.bat` | **CRLF**（＋ASCIIかcp932） | LF / UTF-8 だと**何も表示せずに終わる** |
  | `.js` `.py` などソース | **LF** | Windows の git が CRLF で取り出し、`\n` を置いた照合が0件になる |

  2026-08-19 に上を、2026-08-27 に下を踏んだ。**上だけ書いてあったので下を防げなかった。**
- **パスに空白が入る。** 必ず二重引用符で囲む
- **`bash build.sh` の直後に別のコマンドを貼らない。** bash の標準入力に吸われて実行されない。
  複数を1回で回すなら `&&` / `&` で**1行**にする
- **Python が UTF-8 で書いたファイルを `findstr` で探さない。** `findstr` は cp932 で
  照合するので日本語に一致しない。バッチから拾う行は ASCII で出す
  （`qa_layout_check.py` の `SUMMARY: N findings / M pages`）
- **この環境には、名前だけでは区別できないフォルダが複数ある。**
  出力先を変えても構造は残るので、**やり取りでは常にフルパスを書く**。

  | 通称 | 実際に指しうる場所 |
  |---|---|
  | デスクトップ | `C:\Users\arakida\Desktop` / `OneDrive - adrc.asia\デスクトップ` |
  | 出力先 | `_kumamoto_generator\output\` / 実際の出力先である `LargeScaleDisasters\` |
  | images | `_kumamoto_generator\images\` / `images\<GLIDE>\` |

  実際、`C:\Users\arakida\Desktop` に書いたレポートを「デスクトップに出ます」と
  伝えて探してもらい、往復を1回無駄にした。**ファイルは正しく書けていた。
  名前の指し方だけの問題だった。** 成果物はPDFと同じ場所に置いて曖昧さを減らすが、
  それは対症療法であって、通称で呼ばないことが本体である。

- 相対パスの指示を出さない。`gen_deck.js` は自分の位置から `..\data` `..\images` を見るので、
  置き場所が1階層違うだけで全部外れる

## 手順を出す前にやること

1. **`dir /b` を1回取る。** 想定でコマンドを出して、外れるたびに次を出すのは最悪の進め方
2. **失敗が見える形にしてから進める。** `build.sh` は `soffice` の失敗を `>/dev/null 2>&1` に
   捨てて「built:」と表示する。PDF化が失敗しても気づけない
3. **1コマンドで完結する形を先に渡す。** 貼り付け→スクショ→報告の往復は自動化ではない

## 詰めを下げても消えない重なりは、表ではない（2026-09-14）

ネパールとインドネシアのビルドが `STATUS: FAIL footer-overlap` で落ち、
1ページの詰めを 1 → 0.9 → 0.82 → 0.75 まで下げても消えなかった。
**再試行で消えないときは、原因が表の行数ではない。** 見分け方がある。

| 見えかた | 原因 | 直す場所 |
|---|---|---|
| 詰めを変えると y が動く | 表の行数 | 予算（BUDGET）の調整 |
| **詰めを変えても y が同じ** | **位置が固定の要素** | その要素そのもの |
| y がスライド高（7.5in）を大きく超える | **1行が1ページに収まっていない** | 行を割る |

今回は2つ重なっていた。

### 1. 被害状況の1行が1ページに収まらない（ネパール）

罫線が y=10.105in に出ていた。スライドは 7.5in である。ページ送りの条件は

```js
if (cur.length && h + rh > DMG_BUDGET) { ページを送る }
cur.push(r);
```

で、**1行の高さ rh が予算を超えていても、その行は置かれる。**
送った直後は `cur.length` が 0 なので条件が成立しない。
詰めを下げても行の高さは変わらないので、再試行しても永遠に落ちる。

この災害は被害状況の行が日々伸びる。2026-09-14 時点で最長の行は
**日本語1,395字・英語2,920字**（「避難・要支援者」）。1ページに収まる量ではない。

`apply_dmg_row_split.js` で、予算を超える行を文の切れ目で割る。
2行目以降の項目名に「（続き）」を付け、出典は先頭の行にだけ出す。

### 2. 下部の出典行が2行に折り返す（インドネシア）

罫線が y=7.128in に出て、**どの詰めでも動かなかった。**
`srcLine` は y=6.86・高さ 0.24in に描いており、**下端はちょうど 7.10in で
検査のしきい値と同じ**である。出典が増えて1行に収まらなくなると、
2行目が帯に落ちる。実体はURLの下線だった。

`apply_srcline_fit.js` で、1行に収まるまで文字を小さくする。
それでも収まらなければURLの表示だけ中ほどを省く（**リンク先は変えない**）。

### この2つは、放っておくと必ず起きる

被害状況の行も出典も、**日が経つほど伸びる**。長期化する災害では、
ある日を境に突然ビルドが落ちる。落ちた日は配布物が前日のままになり、
PCが `stale-dist` で見送り、メールも出ない。**1件のレイアウト不具合が
その日のレポートを丸ごと止める。**

## `shrinkText` は LibreOffice では効かない（2026-09-06）

pptxgenjs の `shrinkText: true` は PowerPoint の自動縮小に対応する指定で、
**LibreOffice の PDF 変換はこれを無視する。** `wrap: false` と併用していると、
長い文字列は枠を無視してそのまま伸びる。

2026-09-06、ネパールの時系列が5ページになり、見出しが
「対応の時系列（2026年8月25日〜9月5日（ネパール標準時 UTC+5:45））（1/5）」
まで伸びて、**右上の ADRC ロゴの下に 51pt 潜り込んだ**（p.2〜p.6 の5ページ）。
枠は `w: 11.3` と正しく指定されていたが、効いていなかった。

**PPTX を PowerPoint で開くと縮んで見えるので、そちらだけ見ても気づけない。**
気づけたのは `qa_layout_check.py` が「画像と重なり 68%」を出したからである。

対処は `apply_title_fit.js`。自前で幅を測り、収まるまで fontSize を下げる。

### 文字幅の見積もりは実測で較正する

素朴な「全角1em / 半角0.5em」では、実測より**約19%小さく**出た。
この見出しは 10.35in と見積もられたが、実測は 12.28in だった。
太字ゴシックと LibreOffice の代替フォントは、その仮定より横に広い。

較正した 1.20 / 0.60 を使っている。**少し縮みすぎるのは無害だが、縮み足りないと
ロゴに潜り込む。** どちらへ倒すかを決めておくこと。

### ビルド後に qa_layout_check.py を通す

`build_event.js` は `check_footer_overlap.py`（フッター帯との重なり）は見るが、
**画像との重なりは見ていない。** 今回の重なりはそちらだった。

```bash
python3 generator/scripts/qa_layout_check.py <PDF>
```

`STATUS: OK` は「文字がどこにも重なっていない」ことを意味しない。

## クラウド側のネットワークポリシー（外部サイトの取得が弾かれたとき）

Claude がクラウド上で外部サイトを取れないとき（`EGRESS_BLOCKED`）、原因は
**cloud environment のネットワークアクセス設定**である。既定の `Trusted` は
パッケージレジストリ・GitHub など既定の許可リストだけを通し、それ以外は全部止まる。

**設定場所を間違えやすい。** 「設定 → Claude Code」のページには**無い**。
公式ドキュメントに「There's no settings page or direct URL for the selector」と明記されている。

正しい経路:

1. `claude.ai/code` を開く
2. **メッセージ入力欄のすぐ上の行**にある**雲アイコン**（現在の環境名 = 通常 `Default`）をクリック
3. 環境名の行にマウスを乗せる → 右に出る**歯車アイコン**をクリック
4. **Network access** を `Custom` にする
5. **Allowed domains** に1行1ドメイン（`*.` 前置でサブドメイン全部）
6. **`Also include default list of common package managers` にチェックを入れる**
   ← 外すと npm / GitHub まで止まる

| Level | 外向き通信 |
|---|---|
| None | なし |
| Trusted | 既定の許可リストのみ（初期値） |
| Full | 全ドメイン |
| Custom | 自分の許可リスト（既定リストの併用は任意） |

反映について、ドキュメントには「セッション開始時」とあるが、**2026-08-28 に
稼働中のセッションへ即座に効いた**。設定直後に `check_sources.js` を回せば分かる。
効いていなければ新しいセッションで取り直す。

出典: https://code.claude.com/docs/en/cloud-environments

### 「届かない」を1色で塗らない（2026-09-01）

**遮断とサイト側の不調は、打つ手が違う。**

| curl の言い分 | 意味 | 打つ手 |
|---|---|---|
| `CONNECT tunnel failed, response 403` | ポリシー拒否。トンネルが開かない | 許可リストへの追加を頼む |
| `Connection reset by peer` | トンネルは開いた。上流が切った | **頼んでも直らない** |
| `Operation timed out`（接続は即座） | 同上。サイトが応答していない | 同上 |
| `Could not resolve host` | 綴りかDNS | 綴りを確かめる |

2026-09-01、`dhm.gov.np` がこれで紛れた。8月28日には 200 が返っていたのに
`check_sources.js` が「接続できない（遮断）」と一律に出したため、
**許可済みのドメインをもう一度足させるところだった。**
curl の stderr を読めば区別できる。`check_sources.js` は分けて表示するようにした。

**許可リストの追加を頼む前に、トンネルが開いているかを見る。**
開いているなら、それは相手のサイトの話であってこちらの権限の話ではない。

あわせて、**403 を見たその場で「使えない」と結論しない。**
同じ日、`www.youtube.com` は許可リスト追加の直後は 403 だったが、
しばらく置くと 200 になった。反映に時間差がある。

### 弾かれたときにやってはいけないこと

`/root/.ccr/README.md` にある通り、**TLS検証を切らない・`HTTPS_PROXY` を消さない・
組織ポリシーの拒否（403/407）を再試行しない**。回避せずに報告する。
迂回するより、上の設定を1回入れるか、人が手元で画像を保存する方が速い。

## 定期タスク（cron）は main を clone して始まる

**定期タスクは毎回まっさらなセッションで、環境の既定ソース（`refs/heads/main`）を
clone して始まる。** 前回の作業ブランチは引き継がれない。

スキル一式が main に入っていない間は、**プロンプトの1行目でブランチを取りに行かないと
参照先のファイルが1つも存在しない。** `skills/` ごと無い状態から
「`skills/disaster-report/SKILL.md` を読め」と言われるので、
途中まで動いて手詰まりになる。エラーらしいエラーも出ないため気づきにくい。

2026年8月20〜24日のコロンビア日次タスクはこれで全滅していた。
10回近く発火して、ブランチに1件もコミットが増えていないのが証拠。

### 定期タスクのプロンプトに必ず入れる

```bash
git fetch origin <branch> && git checkout <branch>
test -f skills/disaster-report/SKILL.md || { echo "スキルが見つからない。中断する。"; exit 1; }
```

**存在確認まで書く。** checkout だけ書いても、失敗したときに気づかず先へ進む。

### 根本的にはどちらか

- スキルを main に入れる（マージすれば checkout の1行は要らなくなる）
- 入れないなら、**定期タスクを作った時点で必ずこの3行を先頭に置く**

新しい災害の cron を作るときも同じ。SKILL.md §0「新規イベントの追加」の
cron 2本を作る手順は、この前置きとセットで初めて動く。

### MCP から作った定期タスクにはコネクタが付かない

`create_trigger`（MCP）で作ったタスクは、**Superhuman などのコネクタを持たない
セッションを起こす。** 戻り値にこの警告が出るが、それが唯一の手がかりで、
タスク自体は正常に作られたように見える。

> without connector (mcp__<server>__*) tools

つまり **MCP から作った送信タスクはメールを送れない。**

| **メール送信・カレンダー等コネクタを使う** | **claude.ai の Routines 画面** |

貼り付け用の本文は `references/daily-mail-routine-prompt.txt`、

2026年8月24日、コロンビアの送信タスクをこれで一度作り直した。

で拒否された。回避策は無いので、画面で作る以外にない。

**つないであるコネクタは既定で全部入っている**ので、

### 連鎖して止まったとき、どこで気づけるか

クラウドのビルドが落ちると、PC → メールの順に静かに止まる。
**止まったこと自体を知らせる仕組みは無い。** 手がかりは3つ。

| 見るもの | 止まっている印 |
|---|---|
| `dist` の `manifest.txt` の `BUILT_DATE_JST` | 当日でない |
| `_published/<GLIDE>.skipped.json` の `skipped_at_jst` | 当日（PCは動いたが見送った） |

## Windows の git は改行を CRLF にして取り出す

Git for Windows の既定は `core.autocrlf=true`。**リポジトリに LF で入っていても、
チェックアウトすると CRLF になる。**

パッチの照合は行末に `\n` を置いている。たとえば

```js
{ name: "const d", re: /^[ \t]*const\s+d\s*=\s*JSON\.parse\([^\n]*\)\s*;?[ \t]*\n/m }
```

`[ \t]*` は `\r` を吸えないので、CRLF だと**0件になって当たらない**。
クラウド（LF）では通り、Windowsだけ落ちる。しかも「ファイルが改修されている」
という趣旨のメッセージが出るので、原因を取り違えやすい。

2026年8月27日、コロンビアの初回セットアップでここに当たった。
`const DATA` と `const OUT` は `[^\n]*\n` で `\r` を吸えたため通り、
`const d` だけが落ちた。**3文のうち1文だけ落ちる**のが特徴。

### 対処（両方入れてある）

- `build_event.js` は一時コピーを **LF に正規化してから**パッチを当てる
- `apply_all.js` も、対象が CRLF なら正規化してから当てる（その旨を表示する）
- リポジトリ直下の `.gitattributes` で `* text=auto eol=lf`、`*.bat text eol=crlf`

**`.bat` は CRLF のまま**でなければならない。LF にすると cmd が何も表示せずに終わる。

## `STATUS: FAIL footer-overlap` が、実は重なりではなく `pdfplumber` のクラッシュだったことがある（2026-09-27）

```

pyo3_runtime.PanicException: Python API call failed
```

このコンテナの既定 `python3` は 3.11 だが、apt の `python3-cffi-backend` は
**3.12 用の `.so` しか持っていない**（`/usr/lib/python3/dist-packages/_cffi_backend.cpython-312-*.so`）。
そのため 3.11 側の `cryptography`（pdfminer が使う）が `_cffi_backend` を読めずに
Rust拡張がパニックする。`build_event.js` はこの例外による非ゼロ終了を
「重なりが検出された」と同じ扱いにしているため、**中身を見ずに footer-overlap 失敗と誤認する。**

区別のしかた: `check_footer_overlap.py <PDF>` を単体で実行し、出力が
Pythonのトレースバック（`pyo3_runtime.PanicException` 等）なら環境の問題。

対処（このセッションで実施。次回また消えている前提で書く）：

```bash

```

（`--ignore-installed` が要る。apt 版の `pycparser` と衝突して `Cannot uninstall` で
素の `pip install` は止まる。）ソースからビルドするので `python3.11-dev` / `libffi-dev` / `gcc`
が要るが、いずれもこのイメージには最初から入っていた。直った後は
`python3 -c "import pdfplumber"` が例外を出さないことで確認できる。

**`pdfplumber` を使う他のQAスクリプト（`qa_layout_check.py` 等）も同じ理由で無言のまま
誤った結果を出しうる。** 「検査を通った」を鵜呑みにする前に、単体実行で
トレースバックが出ていないか確認すること。

それでも公開記録の日付は「2026-09-18」なので、`verify_published.js` は
**SEND-OK を返した。前日の版を添付して送るところだった。**

### 直し方

公開記録には PC が出した版の `edition` と `stamp` が入っている。
イベントJSONの今の値と突き合わせれば、PC が作り直しに追いついているか分かる。
違えば `STATUS: NO-SEND stale-onedrive`。

**作り直して比べるのとは違う。記録どうしの照合なので、PDF の非再現性は関係ない。**
（作り直して比べる方式が構造的に必ず落ちる件は、このファイルの別項にある）

### 順番の問題は残っている

PC の定期実行が 08:10 固定で、クラウドの配布が 08:07〜08:13 に散る以上、
**PC が配布より先に走る日がある。** 当面は `stale-onedrive` で止めて

- PC 側の定期実行を後ろへずらす（08:30 など）← **これを採った**
- PC 側が `dist` の `BUILT_AT_JST` を見て、当日ぶんが揃うまで待つ／再試行する
- クラウド側の配布完了を合図にして PC を走らせる

**「当日かどうか」だけを見る検査は、同じ日の中の前後を区別できない。**

### 決めたこと（2026-09-18、荒木田さんの判断）

**PC の定期実行を 08:10 → 08:30 へ移す。** あわせて送信タスクを 08:30 → 08:50 へ。

```

PC       08:30  dist から取得 → LargeScaleDisasters へコピー → 公開記録をプッシュ
クラウド 08:50  公開記録を確認 → ゲート → 送信
```

**`schtasks /create` は、既に登録されているタスクには呼ばれない。**
`TASK_TIME` の定数を書き換えるだけでは、相手のPCは 08:10 のまま動き続ける。
`publish_local.js` に `retimeTask()` を足し、登録済みの側にも
`schtasks /change /st` を毎回当てるようにした。**バッチを1回動かせば移る。**

送信タスクは claude.ai の Routines 画面で作られている（`created_via: "http_api"`）ため、
**MCP の `update_trigger` では時刻を変えられない。**画面から変更してもらう。

余裕は 14 分（配布 08:16 → PC 08:30）。ビルドが長引いた日は
`stale-onedrive` で止まり、バッチの再実行で復旧する。**黙って古い版が出ることはない。**

## 定数を書き換えても、相手のPCは移らない（2026-09-24）

2026-09-18 に PC の定期実行を 08:10 → 08:30 へ移した。
`publish_local.js` の `TASK_TIME` を書き換え、登録済みのタスクにも
`schtasks /change` を当てる `retimeTask()` を足して、
「次にバッチを1回動かしたときに移ります」と伝えた。

**6日経っても 08:10 のまま走っていた。**

| 日付 | PCの実行時刻 |
|---|---|
| 09-18 | 08:10 |
| 09-24 | **08:10** |

理由。定期タスクが呼ぶのは `daily_publish.bat` で、こちらは `--setup` を付けない。

```
ADRC_setup_and_publish.bat  →  publish_local.js --no-pull --setup   → registerTask() → retimeTask()
daily_publish.bat（定期）   →  publish_local.js                     → **何もしない**
```

`registerTask()` は `SETUP` のときしか呼ばれない。つまり
**時刻を直す経路が定期実行側に無かった。**
人が `ADRC_setup_and_publish.bat` を踏まない限り、いつまでも移らない。

### 直し方

毎朝の実行からも `retimeTask()` を通す。既に正しければ1行出して終わる。

```js
if (SETUP && !CHECK) registerTask();
else if (!CHECK && process.platform === "win32" && taskExists()) retimeTask();
```

開始時刻の表記は環境で揺れる（`8:10:00 AM` / `08:10:00` / 日本語ロケール）ので、
`startTimeHHMM()` で 24時間表記に正規化してから比べる。
読めなければ黙って `schtasks /change` を当てる（同じ値でも害がない）。

**「次から移ります」と言った時点では、まだ何も移っていない。**
相手のPCに届く経路が実際にあるかを、言う前に確かめること。

## cp932 のコンソール出力を utf8 で読むと、正規表現が黙って外れる（2026-09-28）

公開記録に `start_time: null` が並んだ。
`schtasks /query /tn ... /v /fo LIST` を `encoding: "utf8"` で読み、
`/^(?:Start Time|開始時刻):/` で拾っていた。**このPCのコンソールは cp932 である。**
日本語の項目名が化けるので当たらない。**英語ロケールなら通るので、こちらでは再現しない。**

例外は出ない。`null` が入るだけである。

### 対処

**ロケールに依らないものを読む。**

```js
// (Get-ScheduledTask -TaskName '...').Triggers[0].StartBoundary
//   → "2026-09-18T08:10:00"  ASCII のみ。化けようがない
const m = /T(\d{2}):(\d{2})/.exec(out);
```

是正も `Set-ScheduledTask`（PowerShell）を先に試し、失敗理由を英語で受け取る。
`schtasks /change` は落ちたときの控えに回し、読むときは `latin1`
（バイトを保つだけ。化けても例外にしない）。

**そして、変えたあとに読み直す。** 「成功した」と出ているのに何も起きていないことがある。
`_published/<GLIDE>.json` の `task.last_change` に before / after / method / ok / error を残す。

### もうひとつの学び

`verify_published.js` は、この `start_time: null` のとき**1行も出さなかった。**
`matches === false` と `start_time` が真であることの両方を条件にしていたためである。
**一番見たかった場合が、一番静かだった。**
「読めた／ずれている／一致している」の3つは、必ず別の分岐にする。

## 縮めたら、落ちたものを数える（2026-09-28）

`SKILL.md` にあるか確かめた。** 2つ落ちていた。

|---|---|

機械的に抜いて `grep` する。目で読み比べない。**読み比べは落ちたものを見つけられない。**

```bash
git show <縮める前>:<プロンプト> \
  | grep -oE '`[a-z_]+\.js`|get_draft_send_status|…' | sort -u \
  | while read t; do grep -q "$t" SKILL.md || echo "** 無い: $t"; done
```

`MISSING_SKILL` のように**入口にしか要らないもの**は落ちていて正しい。
落ちたもの全部を戻すのではなく、1件ずつどちらに属するかを決める。

対処: 07:45 以降にもう一度このファイルを実行してください。」

### 一般化

**人の操作の時刻を仕様にしない。** 「07:45以降に踏んでください」は仕様ではなく願望である。
いつ踏まれてもよいように作る。待てるものは待つ。

## 試験はプッシュだけ止めても漏れる。書き込みも止める（2026-10-05）

`--wait` の挙動を `--dest <試験用フォルダ>` で確かめた。
`--dest` を付けるとプッシュしない作りにしてあったが、
**記録の書き込みは止めていなかった。**

`_published/EQ-2026-000146-COL.skipped.json` に試験で渡した日付（翌日）が入り、
それを `git add -A` でコミットしてプッシュしてしまった。

```
"skipped_at_jst": "2026-10-06 22:47",  "reason": "stale-dist"
```

送信タスクは「**今日**の見送り記録があれば送らない」と判断する。
翌朝（10-06）にこれを読んで、**コロンビアのメールを止めるところだった。**
公開記録のほうも試験で上書きしていた（PCの再実行がたまたま上から書き直した）。

**「試験が本番の判断材料を汚してはいけない」はこのファイルに既に書いてあった。**
止めていたのはプッシュだけで、書き込みは素通りだった。

### 直し方

押さない実行では、記録を**一時フォルダへ逃がす**。

```js
const MARKER_DIR = PUSH ? null : fs.mkdtempSync(path.join(os.tmpdir(), "adrc-markers-"));
```

`writePublished(..., outDir)` と `skipped.json` の両方がこれを見る。
`--dest` だけ、`--no-push` だけでも効く。**押す実行（本番）だけが `_published/` に書く。**

当日ぶんあり／前日ぶんの両方で、本番の記録に差が出ないことを確認した。

### 一般化

- **出口を1つ止めただけでは、副作用は止まらない。** 書き込み・プッシュ・通知を別々に数える
- `git add -A` は、試験が残したものも拾う。**コミット前に `git status` を読む。**
  今回は「ファイルが転送されていない」の調査に気を取られて読まなかった

### 参照先が存在しないことに、誰も気づいていなかった

### 出力99,413トークンの中身

原稿用紙およそ500枚ぶんを毎朝書いていた。内訳は3つ。

1. **全Keyの個別ページを毎回ブラウザで開いて読む**（Step 3.5 が明示的に義務づけ）
2. **docxを毎朝ゼロから書き起こす** — 罫線・背景色・ラベル列・フッタの体裁まで。**毎日同じ**

### `www.adrc.asia` はクラウドから curl で読めない
