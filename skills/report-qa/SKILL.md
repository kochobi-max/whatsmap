# レポートQAスキル

生成済みdocxレポートの品質を機械検証し、人間の確認を「WARN/FAIL項目のみ」に絞る。

## 使い方

### モード1: LDI日次レポート検証（既定）

```bash
python scripts/qa_report.py "<docxのパス>" --type ldi
```

対象: `LDI_CMS_Reports_YYYY-MM-DD.docx`（既定保存先 `C:\Users\arakida\LatestDisasterInfo\`）

### モード2: 汎用docx検証

```bash
python scripts/qa_report.py "<docxのパス>" --type generic
```

災害別レポート・出張報告書など任意のdocxに対し、基本チェック（開封可否・プレースホルダ・空セル・日付）のみ実施。

## 検証項目（--type ldi）

| # | 項目 | 判定 |
|---|------|------|
| 1 | ファイルが開ける・破損なし | FAIL |
| 2 | タイトル「ADRC LDI CMS レポート入力データ」存在 | FAIL |
| 3 | 作成日 = 今日 | WARN（過去日付は古い生成物の可能性） |
| 4 | ヘッダ「全N件」= 実エントリ数 = フッタ「以上 N件」 | FAIL |
| 5 | 各エントリに7行（種類/タイトル日英/内容日英/URL1/URL2）が揃う | FAIL |
| 6 | URL1がhttp(s)で始まる、URL2はURLまたは「—」 | FAIL |
| 7 | 内容（日本語）50〜80文字目安（30未満/120超で警告） | WARN |
| 8 | 内容（英語）40〜80語目安（30未満/100超で警告） | WARN |
| 9 | プレースホルダ残存（XXXX, TBD, [ ], ○○, 例:） | FAIL |
| 10 | 「確認中」「TBC」の残存 | WARN（意図的な場合あり） |
| 11 | GLIDE番号の書式 `XX-YYYY-NNNNNN-XXX` | WARN |
| 12 | 空セルの検出 | FAIL |

## スキル実行時のワークフロー（Claudeへの指示）

1. `scripts/qa_report.py` を実行し、JSON結果を取得する
2. **FAILが1件でもあれば「不合格」**。原因箇所を特定し、修正案を提示する（勝手に上書き修正しない。修正前に必ずユーザー確認）
3. WARN項目は一覧化し、人間が判断すべき点として明示する
4. URLはスクリプトでは形式チェックのみ。**WARN/FAIL対象のURLだけ** Chrome MCP（navigate → ページタイトル確認）で実在確認する（全URL再確認はしない。生成時に確認済みのため）
5. 最後に必ず以下の形式で出力する:

```
## QA結果: <ファイル名>
判定: 合格 / 条件付き合格（WARN n件） / 不合格（FAIL n件）

| 項目 | 結果 | 詳細 |
|------|------|------|

人間が確認すべき点:
- ...
```

## 安全ルール

- このスキルは**読み取り専用**。対象docxを変更・削除しない
- 修正が必要な場合は、修正内容を提示してユーザー承認後に別ファイル（`_fixed`サフィックス）として保存する
