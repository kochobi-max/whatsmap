# GLIDE 突合・ケース分類・対応分析

**目的は対応表を作ることではない。**「なぜ食い違うのか」を類型化し、
「ADRCとして何をするか」を件数で裏づけて示すこと。

---

## 背景（2026年8月時点）

- CREDから説明を受けたデータ不整合について所内分析を実施、`20260815_GLIDE未登録災害_所内説明資料_v1.pptx` を作成済み
- 塩見氏より **EM-DAT・HIPs・WMO-CHE との連携を視野に、Julio氏と Subcommittee 立ち上げ**の提案
- 荒木田の方針: 「互いのDB向上のため他DBを参照し合うガイドラインを定める。
  ただし**登録範囲が異なるので、あくまで自DBが必要とする範囲で**」
- GLIDE全件は HDX から取得できる（Julio氏への個別依頼が不要になった）

> この「登録範囲が異なる」という前提が分類設計の核心。
> **C6（閾値差）は解消すべき不整合ではなく正常な差**であり、分母から外す。
> これを混ぜると「不整合が数万件ある」という誤った危機感を生む。

## 第1層: データ取得（L4・自動）

| ソース | 取得先 | 形式 |
|--------|--------|------|
| GLIDE | HDX `global-glide-events` https://data.humdata.org/dataset/global-glide-events | CSV |
| EM-DAT | EM-DAT public https://public.emdat.be/ | xlsx → **CSVで書き出す** |
| GDACS | イベントAPI（補助・任意） | JSON |
| ReliefWeb | disasters API（GLIDE番号を保持・補助） | JSON |

> スクリプトは**標準ライブラリのみ**で動く（pandas 不要）。EM-DAT は xlsx で配布されるので、
> Excel か LibreOffice で CSV に書き出してから渡す。

## 第2層: 突合とケース分類（L4・自動）

```bash
python3 scripts/match_glide_emdat.py \
  --glide  /path/to/glide.csv \
  --emdat  /path/to/emdat.csv \
  --window 7 \
  --emdat-death-floor 10 \
  --out-matches  out/matches.csv \
  --out-summary  out/summary.csv
```

動作確認:

```bash
python3 scripts/match_glide_emdat.py --selftest
```

### 突合のロジック（2段構え）

1. **明示リンク** — EM-DAT の `Glide` 列に GLIDE 番号が入っていればそれで対応づける（最優先）
2. **キー照合** — `ISO3国コード × 災害種別 × 発生日 ±window日`

災害種別は GLIDE のイベントコード（EQ / FL / TC …）と EM-DAT の Disaster Type / Subtype を
共通キー（earthquake / flood / storm / …）へ正規化してから比較する。
表記ゆれは部分一致で吸収する。

### ケース分類

| コード | ケース | 定義 |
|--------|--------|------|
| **C1** | 整合 | 双方に存在し、国・種別・日付が一致 |
| **C2** | GLIDE未登録 | EM-DAT にあり GLIDE にない |
| **C3** | EM-DAT未登録 | GLIDE にあり EM-DAT にない |
| **C4** | 識別子ずれ | 双方にあるが 国コード / 日付 / 種別分類 が不一致 |
| **C5** | 粒度差 | 1対多・多対1（台風を国別に分割 / 複数洪水を1件に統合） |
| **C6** | 閾値差 | 相手方の登録基準に届かず対象外 ＝ **正常な差・解消不要** |
| **C7** | 重複 | 同一DB内に同一災害が複数登録 |

> **1対多の全件を C5 にすること。** 1件目だけを紐づけて2件目を「GLIDE未登録(C2)」に
> 落とすと、粒度差が未登録として数えられ、対応方針を誤る。実装・自己テスト済み。

## 🚦 分類ルールの妥当性検証（BLOCKING・人）

**初回は必ず、分類結果からサンプル50件を無作為抽出して目視する。**
ルールが間違っていれば全件が間違う。ここがF全体の信頼性の土台になる。

抽出は各ケースから按分（C1〜C5, C7 から件数比で。C6 も5件は見る）。
確認する点:

| 見る点 | 判断 |
|--------|------|
| C2 が本当に GLIDE 未登録か | 表記ゆれで突合できていないだけではないか |
| C4 の「ずれ」が実際にずれか | 日付の定義差（発生日 vs 報告日）ではないか |
| C5 が本当に粒度差か | 別災害を誤って束ねていないか |
| C6 の線引き | `--emdat-death-floor` の値は妥当か。GLIDEの登録思想と合うか |
| 種別の正規化 | GLIDE の LS/MS/AV を landslide にまとめてよいか等 |

**目視で3件以上の誤分類が出たら、ルールを直して全件を再実行する。**

## 第3層: 対応分析（L1〜L2・人が決める）

「対応分析」とは次の3点の定量化である。

1. **各ケースが何件あり、全体の何%か** → 機械が出す
2. **1件解消するのに誰が何をする必要があるか** → **人が決める**
3. **その対応で何件が解消し、何件は原理的に解消しないか** → 機械が出す

| ケース | 原因仮説 | ADRCが取り得る対応 | 効果 | コスト |
|--------|---------|------------------|------|-------|
| C2 | 起票主体が不在 / 要請がなかった | GDACS Orange以上を自動起票候補にする | 集計で出す | 中 |
| C3 | EM-DAT基準未満 or 未把握 | CREDへ定期フィード | 集計で出す | 低 |
| C4 | 種別分類体系・日付定義の差 | **分類対応表を定義し Subcommittee 提案へ** | 集計で出す | 低 |
| C5 | 集計単位の思想差 | 「親子関係」フィールドの新設提案 | 集計で出す | 高 |
| C6 | — | **対象外と明記し、不整合の分母から外す** | — | 無 |
| C7 | 登録オペレーション起因 | 重複検出をCMSに組み込む | 集計で出す | 中 |

### 出力物

1. 分類済みマスタ CSV（`--out-matches`）
2. ケース別集計と時系列推移（`--out-summary`）
3. **所内説明資料（pptx）** — `20260815_GLIDE未登録災害_所内説明資料_v1.pptx` の後継。
   `adrc-briefing-docs` スキルを使う
4. **Subcommittee向け英文提案** — EM-DAT / HIPs / WMO-CHE 連携の論点整理

## 自律度

| 工程 | 自律度 | 根拠 |
|------|--------|------|
| データ取得・突合・分類・集計 | **L4** | 入力が公開データセット、処理が決定論的、出力が内部分析。間違っても誰にも届かない |
| 分類ルールの妥当性検証 | **L1**（人・初回必須） | ルールが誤れば全件が誤る |
| 原因仮説の設定 | L1 | 業務知識の判断 |
| 対応方針の採否 | **L2**（児玉氏・所内） | ④資源配分 — 経営判断 |
| 対外提案文（Julio氏・CRED・Subcommittee） | **L2** | ③人間関係 — 国際機関間の関係 |

**ADRCの6業務のうち、L4に置けるのはこの突合・分類だけ。**

## 注意

- **CREDやJulio氏へ送る文面は必ず人が確認する。** 機械が出した集計をそのまま
  「御DBに漏れが N 件ある」と書かない。登録範囲が異なる以上、片方の基準で他方を
  欠落と呼ぶのは誤り。C6 を分母から外した数字で語ること
- 突合キーに使う日付は「発生日」。EM-DAT の Start Date が報告日である場合があるので、
  C4 が異常に多いときは日付定義の差を疑う
- GLIDE番号の書式は `XX-YYYY-NNNNNN-XXX`。書式外の行はスクリプトが
  `(no-number)#行番号` として扱うので、集計時にその件数も確認する
