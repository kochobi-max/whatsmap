# ADRC業務自動化 設計書 ― 自律度と人のチェックポイント

作成: 2026-08-17 / 対象: 荒木田（ADRC研究部）が Claude Cowork / Claude Code で回している定常業務

この文書の目的は「どこまで機械に任せられて、どこで人が止めるべきか」を業務単位で確定させることです。
結論を先に言うと、**6業務のうち完全自律（人の関与ゼロ）に置けるのは1つだけ**で、
残り5つは「作るところまで全自動 ＋ 出すところで人が1回見る」が上限です。
理由は技術的な限界ではなく、**不可逆性（送信・登録・公開）と数値責任**にあります。

## 1. 自律度の定義（共通言語）

以降すべてこの5段階で表記します。

| レベル | 定義 | 人の関与 |
|---|---|---|
| **L0** | 手動 | 全部 |
| **L1** | 人が起動、機械が作る、人が確認して出す | 起動＋確認 |
| **L2** | 機械が定期起動して作る、**人が承認して出す** | 承認1回 |
| **L3** | 機械が作って**自動で出す**。例外時のみ人を呼ぶ | 例外時のみ |
| **L4** | 完全自律。人は結果すら見なくてよい | なし |

### 設計原則（これが全体の背骨）

1. **不可逆な行為の直前にゲートを置く。** 外部送信・CMS登録・Web公開・経理提出は不可逆。それ以外（収集・照合・生成・保存）は全部自動でよい。
2. **沈黙は障害と区別がつかない。** 「今日は該当なし」も必ず1通出す。
3. **機械QAを通らないものは出さない。** `report-qa` を全成果物の共通ゲートに昇格させ、FAIL なら送信中止＋人に通知。
4. **数値の責任は人が取る。** AIが出した死者数・金額は、出典URLと並べて人が見られる形にする。

## 2. ワークストリーム別 設計

### A. 大規模災害レポート（PPTX/PDF）→ メール送信まで

**現状**: 熊本は完成形（1日2回更新、07:00に研究部へ自動メール）。コロンビア・インドネシアは別立て。
**課題**: 災害ごとにスキル・ジェネレータ・cronを複製している。

**設計 — `disaster-report`（`kumamoto-eq-report` の汎用化）**

```
skills/disaster-report/
  SKILL.md                     # 手順は熊本版を踏襲（言語レイヤ・フォント・QA規約はそのまま）
  generator/                   # gen_deck.js は共通化。イベント固有部を外出し
  events/
    EQ-2026-000135-JPN.json    # 熊本   ← report_data.json 相当
    EQ-2026-000146-COL.json    # コロンビア
    EQ-2026-000150-IDN.json    # インドネシアNTT
  references/sources/
    JPN.md  # 消防庁・気象庁・内閣府・官邸・地整・防衛省・県災対本部
    COL.md  # UNGRD・SGC・IDEAM
    IDN.md  # BNPB・BMKG・BRIN
    _global.md  # ReliefWeb・GDACS・USGS・Sentinel Asia・国際災害チャーター
```

イベントを1件追加する = JSONを1つ作り、cronを1本張るだけ。国別の情報源プロファイルは再利用されます。

**自律度: L3**（07:00 生成→QA→送信を自動、17:00 は生成・保存のみ）

**人のチェックが要る点**

| 工程 | 判断 | なぜ人か |
|---|---|---|
| 初回レポートの本文 | 全ページ目視 | 新しい災害の「型」が正しいか。2回目以降は差分だけ |
| ティア逸脱 | 公式値を報道値が上回った時 | 「安易に大きい数字へ乗り換えない」は人の判断領域 |
| QA FAIL | overflow / 言語混入 / DRAFT残存 | 送信を止める。自動修正させない |
| 数値の急変 | 前報比で死者+50%、住家被害+2倍など | 認定調査の進展か、本当の拡大か、報の取り違えか |

> 熊本SKILL.mdにある「消防庁の報番号を取り違えない」「一部破損と避難指示世帯数を混同しない」は、
> 実際に起きた事故の記録です。**この種の取り違えは機械QAでは検出できない**ので、
> 数値急変ゲート（前報比の閾値超過で人を呼ぶ）を新設します。

### B. LDI日次レポート → メール送信まで

**現状**: `LDI_CMS_Reports_YYYY-MM-DD.docx` を生成して終わり。CMS担当者への受け渡しは手作業。

**設計 — 生成の後ろに3工程を足すだけ**

```
Step 7  docx生成（現行）
Step 8  report-qa 自動実行 ────────── FAIL → 送信中止・荒木田へ通知（メールは出さない）
Step 9  メール本文を組み立て
          件名: ADRC LDI CMS入力データ（YYYY-MM-DD）更新X件・スキップY件
          本文: エントリ一覧表（LDI ID / 災害名 / タイトル / URL）
          添付: docx
Step 10 送信 → CMS担当者
```

**自律度: L3**（PASS時は自動送信、FAIL/WARNのみ人）

**「0件の日」も必ず送る**こと。件名は `本日の更新対象なし（全N件確認済み・スキップY件）`。
沈黙にすると、担当者はスクリプトが止まったのか本当に更新がないのか判別できません。

**人のチェックが要る点**

| 工程 | 判断 | なぜ人か |
|---|---|---|
| QA WARN | 文字数逸脱・「確認中」残存・GLIDE書式 | 意図的な場合があるので機械で切れない |
| CMSへの実登録 | コピー＆ペースト | ADRC CMSに書き込み権限を機械に渡すかは別問題（下記） |
| 登録基準の境界 | 死者9人（アジア加盟国は10人以上）等 | 惜しい案件を落とすか拾うかは編集判断 |

> **CMS自動登録について**: 技術的にはブラウザ自動化で可能ですが、**当面は非推奨**です。
> LDIはADRCの対外公開DBで、誤登録は取り消しが効かず対外的な信用に直結します。
> まず半年「メールまで自動」で運用し、スキップ判定の的中率が安定してから検討するのが妥当です。

### C. 規模エスカレーション（LDI → 大規模災害レポートへの昇格）

**新規要素であり、今回の設計で一番重要な部分**です。
現状はLDIと大規模レポートが独立していて、「これは大きいからレポートを作ろう」の判断が完全に人の頭の中にあります。

**設計 — 昇格判定を LDI パイプラインの Step 5.5 として明文化**

判定は毎朝のLDI処理の中で自動的に走り、該当があれば**起票メールを1通出す**。
レポート作成の開始そのものは**人の承認**を要します。

#### 昇格基準（案 ― 要決定）

| 区分 | 昇格条件（いずれか） |
|---|---|
| **日本国内** | 死者20人以上 / 最大震度6強以上かつ住家全壊確認 / 非常災害対策本部の設置 |
| **ADRC加盟国** | 死者100人以上 / M7.0以上かつ死者確認 / Sentinel Asia EO発動 **かつ** 国際災害チャーター発動 |
| **非加盟国** | 死者300人以上 / チャーター発動かつ国家非常事態宣言 |
| **共通の追加** | ADRCが要請主体となったEO / 日本の国際緊急援助隊派遣 |

> 実績と照合すると、熊本（M7.1・国内）、コロンビア・チョコ（M7.4）、インドネシアNTT（M7.7・EO＋チャーター）
> のいずれもこの基準を満たします。過去の判断と整合するので、出発点として妥当です。
> **数値は暫定です。運用しながら調整してください。**

#### 昇格時の動作

```
検知（自動 L4）
  ↓
起票メール（自動 L3）「この災害を大規模災害レポート対象にしますか？」
  ├ 災害名・GLIDE・現在の被害数値・出典
  ├ 昇格根拠（どの基準に何で該当したか）
  └ 承認したときに何が起きるかの明示（1日2回生成／07:00に研究部へメール）
  ↓
人の承認（← ここが唯一の人手）
  ↓
events/<GLIDE>.json 生成 ＋ cron 2本作成（自動 L3）
  ↓
以降 A の運用へ
  ↓
終了判定（自動 L3）… 3日間、数値の更新も新規情報もなければ
                     「レポート更新を終了しますか？」を1通出す
```

**人の承認を残す理由**: 承認した瞬間から所内メールが毎日流れ、担当者の作業が発生します。
これは技術判断ではなく**組織の資源配分の判断**なので、自動化してはいけない領域です。
逆に「終了」の提案は機械が出してよい（放置してcronが回り続ける方が害が大きい）。

**自律度: 検知 L4 / 起票 L3 / 開始 L2 / 終了提案 L3**

### D. 出張・調査レポート（Plaud連動・領収書を放り込むだけ）

**現状**: `trip-report-creator` は申請書からdocx/xlsxの器を作れますが、
面会者・日ごとの活動内容・交通費明細・宿泊費は**人が全部口頭で入力**しています。ここが最大の手作業です。

**設計 — `trip-dossier`（新規スキル。既存2スキルの前段に立つ収集・抽出層）**

```
入力: 出張フォルダに放り込むだけ
        領収書（写真/PDF）、ボーディングパス、乗換案内スクショ、申請書
        ※ 何も入れなくても Calendar と Plaud だけで骨格はできる

┌ 1. 期間の確定 ─── Google Calendar から出張期間・訪問先イベントを取得
│                   （申請書があれば申請書を優先、なければCalendar）
├ 2. 会議記録 ───── Plaud list_files を期間で絞り、get_note / get_transcript
│                   → 面会者（話者＋自己紹介発話から氏名・所属）
│                   → 日ごとの活動内容ドラフト（報告書「Trip Report」欄）
│                   → 決定事項・宿題（フォローアップ用）
├ 3. 経費 ───────── 領収書OCR → 日付・金額・通貨・費目（交通/宿泊/日当/その他）
│                   ボーディングパス → 区間・便名・搭乗日（交通費の裏付け）
│                   乗換案内スクショ → 国内経路と金額（精算書にそのまま貼付）
├ 4. 突合 ───────── 経費の日付 × 行程の日付 が合うか。合わないものだけ抽出
└ 5. 投入 ───────── trip-report-creator の CLI へ JSON で流し込み
                    → 出張報告書.docx ＋ 旅費精算書.xlsx
                    → 併せて「確認シート」を出す（後述）

おまけ: 写真があれば trip-photo-slides へ連携（目視選定は従来どおり人）
```

#### 確認シート（この設計の肝）

成果物と一緒に、**AIが埋めた欄だけを一覧にした確認シート**を出します。

| 欄 | AIの記入値 | 根拠 | 確信度 |
|---|---|---|---|
| 面会者 | JICA関西 重吉氏 | Plaud 08-12 05:12「JICA関西の重吉です」 | 高 |
| 8/13の活動 | STEP5-6演習の講評 | Plaud 08-13 note | 中 |
| 交通費 15,500円 | 西荻窪〜灘 | 乗換案内スクショ IMG_0412 | 高 |
| 宿泊費 26,900円 | 3泊 | 領収書 PDF p.1 | 高 |
| 日当 1,600円×1日 | — | **AI推定（根拠なし）** | **低** |

人は成果物ではなく**このシートだけを見ればよい**。全欄を読み直す作業がなくなります。

**自律度: L2**（生成まで全自動、提出は必ず人）

**人のチェックが要る点**

| 工程 | 判断 | なぜ人か |
|---|---|---|
| **金額** | 全件 | 1円違えば経理差戻し。OCRは桁・通貨記号を間違える |
| **面会者の氏名・肩書** | 全件 | 音声からの氏名認識は誤りが出る。相手先に失礼が生じる |
| **発言の帰属** | 「誰が何を言ったか」 | 話者分離の誤りは、報告書に書かれると実害になる |
| **非公開情報** | 録音に含まれる人事・未確定案件 | 報告書は所内回覧される。Plaudの内容をそのまま書けない |
| 日当・宿泊の規程適用 | 上限額・区分 | ADRC規程の解釈は人 |

### F. GLIDE ― 対応表 → ケース分類 → 対応分析

**現状**（メールから確認）:

- 荒木田がCREDから説明を受けたデータ不整合を分析し、`20260815_GLIDE未登録災害_所内説明資料_v1.pptx` を作成、塩見さんへ照会中
- 塩見さんの回答: HDXに `global-glide-events` があるので全件エクスポートは以前より容易。
  **EM-DAT・HIPs・WMO-CHE との連携を視野に、Julio氏と Subcommittee 立ち上げを提案**
- 荒木田の返信: 「互いのDB向上のため他DBを参照し合うガイドラインを定める、ただし登録範囲が異なるので自DBが必要とする範囲で」

つまり**単なる突合表ではなく、「なぜ食い違うのか」の類型化と「ADRCとして何をするか」まで**が求められています。

**設計 — `glide-analysis`（3層構成）**

#### 第1層: データ突合（決定論的・L4）

| ソース | 取得 |
|---|---|
| GLIDE | HDX `global-glide-events`（CSV） |
| EM-DAT | CRED public dataset |
| GDACS | イベントAPI（alertlevel別） |
| ReliefWeb | disasters API（GLIDE番号を保持している） |

マッチングキー: `ISO3国コード × 災害種別 × 発生日 ±7日`、副キーとして地名・マグニチュード。
突合結果を1本のマスタCSVにする（両者のID・数値・出典を横に並べる）。

#### 第2層: ケース分類（ルールベース・L4）

| コード | ケース | 定義 |
|---|---|---|
| **C1** | 整合 | 双方に存在し、国・種別・日付・規模が一致 |
| **C2** | GLIDE未登録 | EM-DATにあり、GLIDEにない |
| **C3** | EM-DAT未登録 | GLIDEにあり、EM-DATにない |
| **C4** | 識別子ずれ | 双方にあるが 国コード / 日付 / 種別分類 が不一致 |
| **C5** | 粒度差 | 1対多・多対1（1つの台風を国別に分割 / 複数の洪水を1件に統合） |
| **C6** | 閾値差 | 相手方の登録基準に届かず対象外（＝正常な差、解消不要） |
| **C7** | 重複 | 同一DB内に同一災害が複数登録 |

**分類は機械が全件やる。** ここが今まで人手だった部分で、最も自動化の効く箇所です。

#### 第3層: 対応分析（半自動・L1〜L2）

各ケースに対して以下を組み立てます。

| ケース | 原因仮説 | ADRCが取り得る対応 | 効果（解消件数） | コスト |
|---|---|---|---|---|
| C2 | 起票主体が不在 / 要請がなかった | GDACS Orange以上を自動起票候補に | 集計で出す | 中 |
| C3 | EM-DAT基準未満 or 未把握 | CREDへ定期フィード | 集計で出す | 低 |
| C4 | 種別分類体系の差（例: 土砂災害の扱い） | **分類対応表を定義し Subcommittee 提案へ** | 集計で出す | 低 |
| C5 | 集計単位の思想差 | 「親子関係」フィールドの新設提案 | 集計で出す | 高 |
| C6 | — | 対象外と明記し、不整合の分母から外す | — | 無 |
| C7 | 登録オペレーション起因 | 重複検出をCMSに組み込む | 集計で出す | 中 |

**出力物**: ①分類済みマスタCSV ②ケース別集計と時系列推移 ③所内説明資料（pptx、v1の後継）
④Subcommittee向け英文提案（EM-DAT / HIPs / WMO-CHE 連携の論点整理）

**自律度: 突合・分類 L4 / 原因仮説・対応方針 L1 / 対外提案文 L2**

**人のチェックが要る点**

| 工程 | 判断 | なぜ人か |
|---|---|---|
| 分類ルールの妥当性 | **サンプル50件を目視して分類が納得できるか** | ルールが間違っていると全件が間違う。最初に1回、必ず |
| C6（閾値差）の線引き | どこまでを「正常な差」とするか | GLIDEの登録思想そのものの定義 |
| 対応方針の採否 | 何にリソースを割くか | 経営判断（児玉さん・所内） |
| 対外提案文 | Julio氏・CRED・Subcommitteeへの文面 | 国際機関間の関係 |

> **「対応分析までやってみる」への直接の答え**: 対応分析＝下記3点の定量化です。
> ①各ケースが何件あり、全体の何%か ②1件解消するのに誰が何をする必要があるか
> ③その対応で何件が解消し、何件は原理的に解消しないか。
> ①と③は機械が出せます。②は人が決めます。

## 4. 【本題】人のチェックが必要な場所 ― 一覧

チェックが必要になる理由は5種類しかありません。

| 分類 | 理由 | 該当箇所 |
|---|---|---|
| **① 不可逆性** | 取り消せない | 対外メール送信、CMS登録、Web公開、経理提出 |
| **② 数値責任** | 間違いが対外的な誤情報になる | 死者数・被害数、精算金額 |
| **③ 人間関係** | 信用が毀損する | 大学・海外カウンターパート・国際機関への文面 |
| **④ 資源配分** | 組織の判断 | レポート化するか、どの対応方針を採るか |
| **⑤ 新規判断** | 前例のない型 | 新災害の初回レポート、新しい分類ルール |

### 業務 × チェックポイント 対応表

| 業務 | 全自動でよい範囲 | 人が必ず見る点 | 理由 | 頻度・所要 |
|---|---|---|---|---|
| **A 大規模災害レポート** | 収集・生成・QA・**送信** | 初回本文 / ティア逸脱 / QA FAIL / 数値急変 | ②⑤ | 例外時のみ・5〜15分 |
| **B LDI** | 収集・スキップ判定・生成・QA・**送信** | QA WARN / 基準の境界 / CMS実登録 | ①② | 日次5分 |
| **C 昇格** | 検知・起票・終了提案 | **レポート化の承認** | ④ | 災害ごと1回・2分 |
| **D 出張・調査** | 収集・OCR・抽出・生成 | **金額全件 / 面会者 / 発言の帰属 / 非公開情報** | ①②③ | 出張ごと・15〜30分 |
| **E セミナー** | 読解・整理・逆算・下書き | **全送信 / 科学的内容 / 予算・人選** | ①③ | 都度・5分 |
| **F GLIDE** | 突合・分類・集計 | **分類ルール妥当性（初回50件） / 対応方針採否 / 対外提案文** | ③④⑤ | 初回1回＋方針決定時 |

### 完全自律（L4）に置いてよいもの

**GLIDEの突合・分類だけ**です。入力が公開データセット、処理が決定論的、出力が内部分析で、
間違っても誰にも届かない。この3条件が揃うのはここだけです。

逆に言えば、**残り5業務で「人のチェックをなくす」ことはできません**。
ただし**チェックの中身を「全部読む」から「差分・例外・確信度の低い欄だけ見る」に変えられる**。
それが実際の削減効果です。

## 5. 削減効果（概算）

現在の実績ベース（熊本1日2回・コロンビア継続・LDI日次・出張複数件）からの見積もりです。

| 業務 | 現在 | 自動化後 | 効果 |
|---|---|---|---|
| A 大規模災害レポート | 送信まで自動（実装済み） | 数値急変ゲート追加で**見落とし削減** | 質の向上 |
| A' 災害追加の手間 | 災害ごとにスキル複製 | **JSON 1本 + cron 1本** | 新規災害の立ち上げが数十分→数分 |
| B LDI | 生成後、担当者への受け渡しが手作業 | 送信まで自動 | 日次の手作業が消える |
| C 昇格 | 頭の中の判断（見落としリスク） | 自動検知＋承認1回 | **見落としがなくなる** |
| D 出張・調査 | 面会者・活動・経費を全部口頭入力 | 確認シート15〜30分 | **ここが最大の削減** |
| E セミナー | 全メールを自分で追う | 課題表＋下書き | 締切管理の抜け防止 |
| F GLIDE | 手作業の突合 | 全件自動分類 | 分析可能な規模になる |

**一番効くのは D（出張・調査）**です。理由は、現在ここだけが「機械可読な入力（Plaud録音・領収書画像・Calendar）が
すでに揃っているのに、人が口頭で再入力している」状態だからです。
